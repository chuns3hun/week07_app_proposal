## 1. 검토 방식
- AI 실행 여부: **실행함** — Claude (claude.ai 채팅)
- 짝 검토 여부: **하지 않음**
- 자료 전달 방식: 과제 안내문과 실습 안내문은 대화에 붙여 넣음. proposal.md·context-pack.md는 AI가 작성한 초안을 대화 안에서 검토함. 3~5주차 코드는 AI가 본인 공개 GitHub 저장소를 직접 열어 확인함
- 검토 기준: 확정한 범위, 미정 항목, 자료 충돌, 빠진 조건, AC 확인 절차
- 확인 방법: 초안을 과제 안내문의 "스스로 확인할 내용"과 실습 LAB-AC1~6에 하나씩 대조

## 2. 검토에서 나온 지적

| 구분 | 지적 내용 | 반영 |
|---|---|---|
| 빠진 조건 | 수정·삭제가 없으면 큰 오타(60→600)가 직전 기록으로 남음 | 입력 상한 추가 (아래 3번) |
| 미정 항목 | 기기 저장 방법을 아직 정하지 못함 | 미정으로 두고 한계 명시 |
| 자료 충돌 | proposal.md 실행 환경(Android)과 실습 안내(`-d chrome`)가 다름 | context-pack.md 7절에 기록, 실행 대상은 미정 |
| 빠진 정보 | context-pack에 "현재 상태"와 자료의 최신성이 없었음 | 5개 항목 구조와 최신성 열 추가 |
| 확인 절차 | 숫자 변환(`tryParse`) 문서를 직접 열어 보지 않음 | 자료표에 미정 항목으로 표시 |

## 3. AI 제안과 판단

| # | AI 제안 | 판단 | 이유 |
|---|---|---|---|
| 1 | 앱 후보 B(과제 마감 관리), C(오답 노트) | **거절** | 세 후보 모두 규모는 비슷하지만, 운동 기록은 주 3회 이상 직접 겪는 문제라 사용자와 가치를 가장 구체적으로 설명할 수 있음 |
| 2 | 저장 방식을 미정으로 두고 메모리 저장으로 시작 | **채택(조건부)** | 기기 저장 방법을 아직 수업에서 확인하지 못함. 대신 "앱 종료 시 기록이 사라진다"는 한계를 proposal.md 남은 질문에 명시함 |
| 3 | 기록 수정·삭제를 MVP에서 보류 | **수정** | 그대로 보류하면 60을 600으로 잘못 입력했을 때 틀린 값이 직전 기록으로 표시되어 핵심 가치가 깨짐. 삭제 기능을 넣는 대신 입력 상한(무게 500kg, 횟수 100회)을 추가하고 AC2 확인 값에 600을 넣음 |
| 4 | AC를 요구치(4개)보다 많은 5개로 작성 | **채택** | AC5(빈 종목명 차단)는 종목 추가 기능의 잘못된 입력 조건이라 필요함. 다음 작업 범위에서는 제외해 부담을 줄임 |
| 5 | 직전 기록을 변수로 저장하지 않고 getter로 계산 | **채택** | 5주차 STATE_CONTRACT의 원칙(계산 가능한 값은 저장하지 않음)과 같음. 따로 저장하면 기록 추가 시 갱신을 빠뜨릴 위험이 있음 |
| 6 | 다음 작업에서 종목 추가와 화면 이동 제외 | **채택** | 핵심 가치(직전 기록 확인)를 한 화면에서 먼저 검증하는 것이 우선. 3화면 이동은 그다음 작업 |
| 7 | AI에게 코드 요청 시 완성 코드 전체가 아니라 패턴 부분만 제공 | **채택** | 5주차 PROMPT_COMPARISON에서 완성 코드를 주면 응답이 입력을 반복해 비교 의미가 없었음 |
